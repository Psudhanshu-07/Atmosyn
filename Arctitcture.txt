# Technical Architecture Document

## AI-Based Forecast Bust Detection for Medium-Range Weather Forecasts

**Problem Statement ID:** 26079
**Organization:** Ministry of Earth Sciences (MoES)
**Department:** National Centre for Medium Range Weather Forecasting (NCMRWF)
**Application Type:** AI/ML + Geospatial Web Application
**Primary Objective:** Detect regions and lead times where medium-range NWP forecasts are likely to have high uncertainty or large errors and provide an explainable forecast-confidence indicator.

---

# 4. Data Architecture

The system requires two fundamental types of information:

### Forecast

What the NWP model predicted.

### Observation

What actually happened.

The core relationship is:

```text
NWP Forecast
     +
Actual Observation
     ↓
Forecast Error
     ↓
Bust Label
     ↓
ML Training Dataset
```

Example:

```text
Forecast:
Rainfall = 120 mm

Observed:
Rainfall = 35 mm

Absolute Error:
85 mm

Threshold:
50 mm

Bust:
YES
```

---

# 5. Data Sources

The architecture should support multiple data sources.

### Primary

* NWP forecast data
* Historical NWP forecast runs
* Ground/weather observations

### Optional

* Reanalysis
* Satellite observations
* Radar products
* Ensemble forecasts
* Atmospheric indices

The architecture should **not tightly couple the ML system to one specific provider**.

Use a normalized internal data format so another source can be added later.

# 11. Model Selection

### Initial implementation

Use:

**XGBoost**

because it handles nonlinear relationships and tabular features effectively.

Create baselines using:

* Logistic Regression
* Random Forest

Then compare against XGBoost.

The final model should be selected based on validation performance rather than assuming a particular algorithm is best.

# 12. Bust Detection Logic

Conceptually:

```text
Forecast
   │
   ▼
Expected Error
   │
   ▼
Bust Threshold
   │
   ├── Below threshold → Normal
   │
   └── Above threshold → Bust
```

For example:

$$
Bust =
\begin{cases}
1 & Error > Threshold\\
0 & Error \le Threshold
\end{cases}
$$

The threshold should be determined from the selected weather variable, historical error distribution, and operational requirements.

---

# 13. Confidence Engine

The ML model produces:

```text
P(Bust)
```

The reliability layer converts this into a user-facing indicator.

For a simple initial implementation:

$$
Confidence = 1-P(Bust)
$$

Example:

```text
Bust Probability = 0.28

Confidence = 0.72

Confidence = 72%
```

The system should distinguish this **AI-derived reliability indicator** from the actual meteorological forecast.

---

# 14. Risk Engine

Example configuration:

```text
0–20%     → Very Low
20–40%    → Low
40–60%    → Moderate
60–80%    → High
80–100%   → Very High
```

These are configurable application thresholds and should be validated against historical data.

# 23. Model Training Pipeline

Training should be separate from real-time inference.

```text
Historical Forecasts
        +
Historical Observations
        ↓
Error Calculation
        ↓
Feature Engineering
        ↓
Train / Validation / Test Split
        ↓
Model Training
        ↓
Model Evaluation
        ↓
Probability Calibration
        ↓
Explainability Validation
        ↓
Model Registry
        ↓
Production Model
```

**Important:** split data chronologically rather than randomly when evaluating forecasting performance, to reduce temporal leakage.

# 27. Reliability and Failure Handling

If live weather data is unavailable:

```text
Data unavailable
      ↓
Use last valid forecast
      ↓
Display timestamp
      ↓
Show "Data may be stale"
```

If ML model fails:

```text
Prediction unavailable
      ↓
Do NOT generate fake confidence
      ↓
Show system status
```

This is especially important for an operational-style application.

## 31. Final Architecture Decision

For your project, I recommend this as the **baseline technical architecture**:

```text
                    WEATHER DATA
                         │
                         ▼
                 ┌───────────────┐
                 │ Data Ingestion │
                 └───────┬───────┘
                         ▼
                 ┌───────────────┐
                 │ Data Quality  │
                 └───────┬───────┘
                         ▼
                 ┌───────────────┐
                 │ Feature       │
                 │ Engineering   │
                 └───────┬───────┘
                         ▼
                ┌──────────────────┐
                │ XGBoost ML Model │
                └────────┬─────────┘
                         ▼
             ┌────────────────────────┐
             │ Bust Probability      │
             │ + Expected Error      │
             └───────────┬────────────┘
                         ▼
                ┌─────────────────┐
                │ Calibration     │
                └────────┬────────┘
                         ▼
             ┌────────────────────────┐
             │ Reliability Engine     │
             │ Confidence + Risk      │
             └───────────┬────────────┘
                         ▼
                   ┌──────────┐
                   │   SHAP   │
                   │ Explain  │
                   └────┬─────┘
                        ▼
                   ┌─────────┐
                   │ FastAPI │
                   └────┬────┘
                        ▼
             ┌─────────────────────┐
             │ React + Leaflet     │
             │ Operational Web App │
             └─────────────────────┘
```

**The key architectural principle is:** the application should sit **on top of NWP**, not attempt to replace NWP. Its job is to estimate **where, when, and why the existing forecast may be unreliable**. This directly maps the architecture to the requirements of Problem Statement 26079.
