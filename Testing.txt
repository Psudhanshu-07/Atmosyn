### 1. ML Validation Strategy

The ML model should **not** be evaluated only by random train/test splitting because weather data is strongly time-dependent.

Recommended approach:

```text
Historical Data
      │
      ▼
Chronological Split
      │
      ├── Training Period
      │
      ├── Validation Period
      │
      └── Unseen Test Period
                 │
                 ▼
        Final Model Evaluation
```

Where sufficient data exists, use **walk-forward validation**:

```text
Train: 2022 ───────► Validate: 2023
Train: 2022–2023 ──► Validate: 2024
Train: 2022–2024 ──► Validate: 2025
```

This better represents how the system would operate operationally: historical data trains the model, and a genuinely later period is treated as unseen.

### 2. Validation Metrics

| Component                 | Primary Metrics                                           | Purpose                                                                                              |
| ------------------------- | --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Forecast-error regression | MAE, RMSE, R²                                             | How accurately expected forecast error is estimated                                                  |
| Bust classification       | Precision, Recall, F1, ROC-AUC, PR-AUC                    | How well high-error/bust cases are detected                                                          |
| Probability quality       | Brier Score, calibration curve                            | Whether a predicted 70% probability behaves approximately like a 70% event frequency over many cases |
| Confidence                | MAE/correlation against realized reliability, calibration | Whether confidence meaningfully tracks forecast reliability                                          |
| Historical baseline       | MAE, RMSE, bust rate                                      | Compare AI with simple historical rules                                                              |
| Explainability            | SHAP consistency, perturbation tests                      | Verify explanations reflect model behavior                                                           |
| Data pipeline             | Missing %, duplicate %, invalid %, alignment rate         | Measure input-data quality                                                                           |
| API                       | Latency, throughput, error rate                           | Operational performance                                                                              |
| UI                        | Load time, interaction success, accessibility issues      | Dashboard usability                                                                                  |

### 3. Key Scientific Validation

For a selected historical case:

```text
Historical NWP Forecast
        │
        ▼
AI predicts:
Bust Probability = 0.78
Confidence = 0.22
        │
        ▼
Actual Observation becomes available
        │
        ▼
Calculate Forecast Error
        │
        ▼
Compare:
Predicted Reliability ↔ Actual Forecast Error
```

A successful demonstration should show that **cases assigned higher bust probability tend, over many historical cases, to have larger realized forecast errors**. A single correct or incorrect prediction should not be treated as proof of model quality.

### 4. Important Anti-Leakage Rules

The following information must **not** be available to the model when generating a real-time prediction:

* Future observation for the target valid time
* Actual forecast error for the target forecast
* Future-derived historical statistics
* Post-event weather information
* Any feature calculated using the target observation
* Any information that would not have been available when the forecast was issued

For example:

```text
Forecast issued: 28 Sep
Prediction target: 3 Oct

Allowed:
✓ NWP forecast issued on 28 Sep
✓ Historical errors available up to 28 Sep
✓ Atmospheric conditions available at prediction time
✓ Previous forecast-run changes
✓ Historical bust rates

Not allowed:
✗ Actual weather on 3 Oct
✗ Forecast error calculated using 3 Oct observation
✗ Information generated after 3 Oct
```

This is one of the most important validation requirements because leakage could make the AI appear highly accurate while being unusable operationally.

### 5. Test Dataset Strategy

The hackathon prototype should maintain three explicit datasets:

| Dataset                 | Purpose                                                                 |
| ----------------------- | ----------------------------------------------------------------------- |
| **Training Dataset**    | Train XGBoost regression/classification models                          |
| **Validation Dataset**  | Tune hyperparameters and probability calibration                        |
| **Unseen Test Dataset** | Final, untouched evaluation                                             |
| **Demo Dataset**        | Fixed historical/current-style data used for the hackathon presentation |

The **unseen test dataset must not be repeatedly used to tune the model**.

### 7. Final Acceptance Criteria

The prototype is considered technically validated when:

* Historical forecast and observation records are correctly time- and location-matched.
* Forecast errors can be independently reproduced.
* No future information leaks into model features.
* Bust labels are generated deterministically using documented thresholds.
* ML performance is reported on an unseen historical period.
* A simple baseline is provided for comparison.
* Bust probabilities are calibrated and remain between 0 and 1.
* Confidence scores remain within the defined range.
* Day 1–Day 10 predictions are correctly associated with their lead times.
* Every prediction is traceable to its forecast run, region, variable, model version, and data source.
* SHAP explanations correspond to actual model inputs.
* Missing or stale data results in a safe degraded state rather than fabricated confidence.
* AI reliability alerts are separate from official weather warnings.
* The dashboard values agree with the API values.
* The complete **NWP → historical error → ML → bust probability → confidence → explanation → map/API** workflow runs successfully.
* Limitations and validation results are documented alongside the prototype.
